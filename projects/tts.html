④ 지표를 바꾸자 드러난 첫 소리 지연: 측정 지표가 체감과 어긋나던 것부터 교정.

  • TTFB 는 44바이트 헤더 도착 시각이라 실제 소리 시작 시각과 다름.주지표를 first_play(실제 재생 시작)로 바꿔 재측정, 경합 없는 단건에서도 426ms
  • 원인은 모델이 아닌 직렬로 놓인 버퍼 2개.SDK 읽기 버퍼가 32,768바이트 = 오디오 683ms 분량이 찰 때까지 한 바이트도 내보내지 않는 구조. 4,096으로 낮춰 432 → 134ms(단건 6회 중위)
  • 더 낮추지 않은 근거도 기록.512까지 낮추면 첫 청크는 그대로이고 청크 401개 · e2e 13% 악화라 4,096 채택
  • 두 번째 버퍼는 스트림 홀드백.발화 종료 판정값(500ms)에 묶여 615ms 분량을 붙들고 있던 것을 별도 스위치로 분리(기본 off).판정값 자체는 하향 불가. 200/300 으로 낮추면 문장 안 호흡을 종료로 오판해 STT 누락률 4.4% → 12~14%
  • 합계 426 → 114ms. 두 값 모두 운영 확정값으로 반영(홀드백 0 · 선행 무음 패딩 0), 9월 말 재측정에서도 단건 첫 재생은 엔진 첫 청크 97~102ms + API·전송 약 11ms로 남은 시간의 대부분이 엔진 몫.앞선 A/B 에서 보이던 "홀드백 이득 −501ms"는 선행 무음이 일찍 도착한 착시로, 목소리 도착은 384 → 380ms 로 불변. 실제 레버는 API 가 앞에 붙이던 무음 패딩(기본 200ms)임을 프로브로 확정

② 처리량 천장 진단 → 돌파: "1.7 rps가 천장"이라던 사내 결론을 벤치마크로 반증.

  • 기존 사내 결론은 "약 1.7 rps는 버전 무관한 구조적 천장".버전(0.22/0.24) × executor(mp/uni) 2×2 전수 벤치로 이를 반증
  • 처리량의 몸통은 보코더(Code2Wav)가 launch-bound eager bs≈1로 돌던 것이 CUDA-graph replay + 요청 간 배치 디코드로 바뀐 것.배칭 기계장치는 구버전 이미지에도 있었으나 자체 운영 config(eager 강제·EOS 튜닝·토큰예산)가 봉인하고 있었고, 네이티브 EOS·abort 레이스 수정이 그 봉인을 풀어줌
  • 동일 부하(conc8)에서 0.73 → 1.61 rps, 각자 최대 안정치 0.73 → 3.09 rps(4.2배).자체 패치 3종·EOS 튜닝·문장분할 의존도 함께 제거
  • 안정성도 질적 전환.conc16 진입 시 엔진 사망(3회 재현)하던 것이 conc48 무오류(1,500+ 요청)로
  • 0.22 에서는 executor 를 uni 로 바꿔도 0.68 → 0.73 rps(+6%)에 그쳤고 conc16 에서 엔진 사망. 병목은 executor 가 아닌 엔진 버전. 0.24 로 옮긴 뒤 최대 안정치 3.09 rps(conc32, conc48까지 err=0).측정 조건별 비교는 차별점 ②에 정리

지연 구조 분해: 튜닝에 앞서 TTFB가 어느 구간에서 나오는지부터 계측.엔진 패치에 전처리(prep)와 엔진 첫 청크(큐+prefill+보코더) 지표를 심어 분해.

  • 전처리 3~6ms·API 약 100ms는 고정이고, 동시 요청 수에 선형 비례하는 구간은 엔진 디코드 루프(동시 +1당 약 +20ms)임을 확인
  • 스트림 세마포어를 32→40으로 여는 통상적 처방은 대조 실험 결과 대기 위치만 엔진 안으로 옮길 뿐 SLA는 오히려 악화.세마포어의 역할을 병목 제거 장치에서 과부하 보호막으로 다시 규정
  • 실효 레버를 코덱 좌측 컨텍스트(72→25, CUDA graph capture 목록 정합 수정 동반)와 첫 청크 프레임 수(4→2) 둘로 좁혀 확정. 첫 청크 프레임은 이후 첫 재생 시점 기준으로 다시 재서 5로 조정. 첫 방출이 재생 판정선을 바로 넘어 첫 재생 383→121ms
  • 청크 경계 불연속을 z-검정으로 자동 판정하는 품질 게이트를 통과시킨 뒤 채택

메모리 누수 전수 조사 (vLLM-Omni 엔진)

  • 43시간 롱런에서 stage0(talker) 프로세스의 호스트 메모리가 선형 증가(+943 MiB/43h)하고 플래토에 도달하지 않는 것을 발견.주기 재시작이 필요한 상태에서 원인을 한 건씩 특정해 6건을 모두 수정 (2026.08 ~ 09)
  • ① abort 요청의 송신측 상태 잔류 (주 누수): 회수 경로가 "마지막 청크 전송 성공"에만 걸려 있어, 클라이언트가 끊고 나간 요청의 코덱 프레임 이력과 참조 텐서가 프로세스 종료까지 남음.부하, 할당자, 캐시를 바꾼 4개 구성에서 증가율은 22~296 MiB/h로 13배 차이인데 abort 건수로 나누면 36~56 KB/abort로 일정. 이 불변량으로 원인 확정.abort 시에만 회수하는 최소 패치로 257 → 60 MiB/h (77% 감소)
  • ② KV 블록 ID 리스트 무한 증가: 비우는 호출이 특정 설정 조건에 묶여 있어 한 번도 비워지지 않음 (실기여 ~3 MiB/h, 상류 v0.25에서 같은 취지로 수정됨)
  • ③ SHM 커넥터 키 장부: 키 추가는 송신 프로세스에, 삭제는 수신 프로세스에만 있어 송신측 set이 토큰당 ~26 B씩 자람.첫 수정은 미소비 세그먼트까지 지워 전송 중인 청크를 파괴(중단율 87%)해 롤백하고, "보냈다 ≠ 읽혔다"를 교훈으로 키만 지우는 방식으로 재수정
  • ④ jemalloc 미연결: 이미지에 라이브러리는 있었지만 LD_PRELOAD가 빠져 glibc arena가 메모리를 반납하지 않음.연결 후 +1.51 → +0.33 MiB/h, 선형성 R² 0.90 → 0.22
  • ⑤ 취소 요청 장부: _cancelled_load_reqs에 추가만 되고 삭제 경로 두 곳이 모두 도달 불가 (요청당 108 B).tracemalloc에서 객체 1개가 128 KiB로 커진 것을 set 해시테이블 리사이즈로 읽고, 슬롯 수(8,192)와 요청 수(2,894)가 맞는 것으로 확인
  • ⑥ torch stable ABI 문자열 unbox (남은 누수의 ~89%): 파이썬 객체, GC, 단편화를 모두 배제한 뒤 jemalloc 힙 프로파일로 추적.표집 편향 보정을 넣자 설명률이 10%에서 84%로 올라, stableivalue_conversions.h:766의 new std::string이 해제되지 않는 것을 특정. 새는 호출은 KV 캐시 쓰기 연산 reshape_and_cache_flash의 kv_cache_dtype 인자. 20만 회 최소재현에서 호출당 +31.9 B, 대조군 0.0 B.prebuilt wheel이라 헤더를 고칠 수 없어 KV 캐시 쓰기의 eager 호출을 순수 torch 스캐터로 우회하고, 6개 형상 × 3개 헤드 구성 18건 동치 검증과 통제 A/B 성능 중립을 확인한 뒤 적용

과제 배경

상담센터를 타깃으로 제안할 자사 TTS 솔루션을 신규 구축하는 과제.기존 시스템 교체가 아니라, 실시간 상담에 쓸 수 있는 응답 속도와 음성 선택지를 갖춘 제품을 처음부터 만드는 것이 목표였음.모델 선정부터 서빙 아키텍처, 백엔드·프론트엔드, 배포·운영까지 전 구간을 단독으로 맡았고, 고객사 PoC·시연까지 진행.현재 사내 솔루션에 적용돼 운영 중.

시스템 구조

시스템 아키텍처: FastAPI WebSocket/REST 게이트웨이 + vLLM-Omni(Qwen3-TTS) 추론 엔진 + Redis 분산락 & 캐싱 + React 대시보드.문장 단위 논리 청킹 및 WebSocket 스트리밍으로 TTFB 단축.

기능 확장: 참조 음성 3~10초만으로 화자 목소리를 복제하는 ICL 기반 음성복제 기능 구현.

  • OpenAI TTS API 호환 인터페이스 + 기존 WebSocket 프로토콜 호환 레이어로 외부 서비스가 코드 수정 없이 연동.세 번째로 Soniox TTS WebSocket 형식을 추가, 클라이언트가 텍스트를 조각으로 흘려보내면 문장 경계마다 합성 큐에 넣고 스트림별 순서는 지키되 스트림끼리는 병렬 처리. PCM·μ-law·A-law·WAV, 8~48kHz, Python·TypeScript SDK 동봉
  • Redis 기반 Atomic quota·분산락·Circuit Breaker 등 장애 대응 로직
  • Whisper 기반 CER/WER 자동 품질 측정 파이프라인
  • 10개 언어 지원 (vLLM 엔진 기준. CPU 엔진을 쓰던 동안은 Supertonic 31개를 합쳐 중복 제외 32개, 2026.10 CPU 엔진 제거로 정리)
  • ITN 정규화 정확도 50.1% → 70.9% (검증셋 기준)

운영: 초기에는 vLLM(GPU)·Supertonic(CPU) 듀얼 엔진으로 장애 시 Circuit Breaker가 CPU 엔진으로 폴백하는 구조.운영 서버에서 CPU 엔진을 쓰지 않는 것이 확정돼 2026.10 제거하고 vLLM 단일 엔진으로 정리(서킷이 열리면 503 응답).쓰지 않는 torch 의존성도 걷어내 API 이미지 6.34GB → 1.16GB

  • 무중단 롤링 재배포 체계 + 온보딩 가이드·운영 런북·장애복구 절차·성능 명세 문서화로 다른 담당자가 이어받을 수 있도록 정리
  • 배포 직후 활성 음성별 prefill 워밍과 정형 인사말 프리캐시를 자동 실행, 첫 사용자가 콜드 경로를 밟지 않게
  • 스트리밍 품질을 자동 감지해 자가 치유 (위 차별점 ① 참조).품질 사고가 캐시에 굳는 것을 차단

핵심 엔지니어링

  1. 스트리밍 팝 노이즈: 스트리밍 중 간헐적으로 '틱' 잡음 발생.PCM 청크가 홀수 바이트로 끊겨 와 16bit 샘플 정렬이 깨지는 것이 원인.잔여 바이트를 다음 청크에 이어 붙이는 Residual Buffer로 정렬을 보장하고, 청크 경계에 Micro-fade를 적용해 해결
  2. 스토리지 누수: 보이스를 삭제해도 디스크 사용량이 계속 증가.원본을 지워도 파생된 MD5 해시 캐시 파일이 남는 구조여서, 파생 파일까지 추적해 함께 지우는 Deep GC를 구현해 차단
  3. 웹소켓 세션 탈취 방어: 비밀번호를 바꿔도 이미 발급된 토큰으로 웹소켓 연결이 열리는 허점 발견.토큰 발급 시점과 password_changed_at을 대조해 변경 이전 토큰을 전부 무효화
  4. ITN 정규화: URL·이메일을 한국어로 부자연스럽게 읽는 문제.자연스러운 발음으로 변환하는 스마트 ITN 엔진을 직접 개발해 정규화 정확도 50.1% → 70.9%
  5. CPU 스파이크 (ReDoS 가드 오버헤드): 정규식 치환의 ReDoS 방어용 ThreadPoolExecutor(max_workers=1) 가드가 치환마다 새로 인스턴스화되어 다수 합성 시 CPU 스파이크와 지연을 유발.오버엔지니어링된 가드를 철거하고 네이티브 C 구현체(re.sub) 동기 호출로 교체해 핫 패스 병목 제거.다만 방어를 없앤 채로 두지 않고 11월에 재설계 — 런타임 가드 대신 사용자 정규식을 저장 시점에 시간 측정해 다항 백트래킹을 거부하고, 길이 0 일치 패턴(\b·lookaround)은 치환이 공백·구두점일 때만 허용. 통과한 검사 결과만 캐시해 워커당 1회로 비용 고정
  6. 전면 백색소음 장애: vLLM 0.24 전환 직후 모든 합성이 백색소음으로 재생되는 문제를 추적해, 엔진의 SSE(JSON) 응답이 그대로 PCM으로 재생된 것이 원인임을 확인.응답 포맷을 오디오로 강제해 해결
  7. 스트리밍 WAV 헤더 정리: 엔진이 문장마다 RIFF 헤더를 붙여 보내 클라이언트 디코딩이 어긋나는 문제.문장별 헤더를 걷어내고 세션 전체에 스트리밍 WAV 헤더를 한 번만 내보내는 구조로 정리해 해결
  8. 크래시로 오진할 뻔한 스트림 집단 절단: 고부하 burst 중 스트림이 무더기로 끊기고 수 분간 무응답.엔진 크래시로 보였으나 컨테이너 재시작 횟수가 0인 것을 확인하고 가설 폐기.실체는 과부하 구간에서 엔진의 "sr concat" 경고(업스트림이 인정한 무해한 로그)가 무더기로 뜨는 사이 API의 vLLM 서킷이 열리고, 폴백이 빈 응답을 반환한 연쇄.동시 한도를 실링(40)보다 한 티어 낮춰(36) 과부하 진입 자체를 완화
  9. HTTP 스트림 tail 지연: 저지연을 표방하면서 실제로는 tail 버퍼를 문장 끝까지 붙들어, 약 615ms 분량이 모일 때까지 한 바이트도 내보내지 않던 구조.WebSocket 경로에만 있던 무음 감지 기반 조기 flush를 HTTP에 이식해 단문 TTFB와 문장 경계 끊김을 함께 해소

2인 체제 설계와 인수인계

  • 역할 분담에 앞서 커밋 기록부터 집계: 최근 90일 커밋 1,256건 전부 1인 작성.문제를 역할 분담 부재가 아닌 인수인계 부재로 진단하고 그에 맞춰 설계
  • 분담 축을 프론트/백엔드 같은 층이 아니라 런타임 품질 ↔ 제품 표면으로 설정.변경량 상위(프론트·배포·UI)와 되돌리기 비용 상위(엔진 패치·ITN·누수)가 한 사람에게 몰리지 않도록 배분하고, 블록 안에서는 단독 결정권을 주되 맞닿는 인터페이스 5개와 2인 승인 6종만 공동 통제
